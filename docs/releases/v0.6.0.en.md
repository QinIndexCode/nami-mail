# Nami Mail 0.6.0

[简体中文](v0.6.0.zh-CN.md) | [English](v0.6.0.en.md)

Nami Mail 0.6.0 is a milestone release: the mail database becomes **fully encrypted at rest**, batch operations and sending are rebuilt on a **persistent task layer**, attachments gain **13 in-place preview formats**, and external CLI/MCP permission failures start **explaining their own fix**. It is also the **first real in-app automatic upgrade** since the updater fix in 0.5.1.

## Read before upgrading: this update cannot be downgraded

- **Database format change**: 0.6.0 switches the SQLite driver to an encrypted build (ChaCha20-Poly1305 whole-database encryption) and migrates the schema from v2 to v4. **After upgrading to 0.6.0 and completing its first launch, you cannot roll back to 0.5.1 or earlier** — older builds cannot read the encrypted database. If you want a safety net, back up the entire `%APPDATA%\Nami Mail` directory first (the data directory holds a key bound to the current Windows user; it is not portable across machines or users).
- **Encryption conversion on first launch**: the first 0.6.0 launch upgrades the existing plaintext database to an encrypted one (verified, then swapped into place atomically). Unexpected power loss or exit mid-conversion has multiple recovery paths: a verified encrypted copy is adopted, an unreadable one is quarantined (`.unreadable`) with a warning, and an intact main database means the conversion simply restarts — no path silently loses data and starts over empty.
- **In-place upgrade preserves everything**: mail, accounts, settings, and encryption keys survive the upgrade; no re-login or reconfiguration is required.

## Download and upgrade guide

- **On 0.5.1: in-app updates are restored** — from `0.5.1` you can detect, download, and "restart and update" straight to `0.6.0` inside the app. The updater fixes from 0.5.1 carry forward hardened in this release (including a fix for update-helper launches failing when the data-directory path contains characters such as `&`).
- **On 0.4.3 or 0.5.0**: those builds bundle the old broken updater and cannot update in-app; download the installer from the Release page and install `0.5.1` manually first (or install `0.6.0` directly).
- Download only the Windows `.exe` installer listed on the Release page. The versioned ZIP, JSON update manifest, `latest.yml`, and `.blockmap` are distribution and in-app update resources, not manual installers.

## Update and signing status

- Code gates: full CI verification passed (typecheck / lint / all workspace tests / e2e / real-chain e2e / desktop smoke / production dependency audit); installer assets and signature status are as listed on this Release page.
- The `0.6.0` Windows installer keeps the **Ed25519 manifest signature** as its update trust root; it is not Authenticode-signed, so Windows SmartScreen may show an "unknown publisher" warning. Do not bypass Windows security warnings; obtain installers only from this Release page.
- In-place upgrades preserve existing local data; re-login or re-authorization is not required.

## What's new

- **Encryption at rest**: the mail database, image caches, and sensitive files are encrypted on disk, with the master key protected by Windows DPAPI for the current user. A copy of the database or cache directory no longer reveals message bodies, subjects, or credentials.
- **Unified task layer**: batch move, flag, archive, undo, send, and snooze become persistent tasks — effective on click, safe across restarts, with undo following the reverse task to settlement; after a provider rebuilds a mailbox (UIDVALIDITY change), old tasks no longer write to the wrong message.
- **Send returns immediately**: clicking send responds instantly (202 + an optimistic local Sent row) while SMTP delivery moves to a background task; the provider's Sent copy is claimed by a stable identifier on sync instead of inserting a duplicate.
- **Attachment preview (13 kinds)**: PDF (strict mode), images, audio/video, text/code, Markdown, Word/Excel/PowerPoint, and archives read in place. Preview runs a fetch → decode → document → render pipeline where every format has explicit budgets and failure explanations; a hostile file at worst shows "can't preview" rather than executing. Remote images and avatars go through a same-origin proxy, so the browser no longer talks to third parties directly.
- **External CLI / MCP that explains itself**: permission failures now carry an actionable suggestion (which settings page, how to re-pair, what to do when the confirmation dialog is unavailable); `namimail status` shows the caller identity, tier, and expiry in one command.
- **Startup and failure resilience**: an interrupted encryption conversion never becomes an empty database, large-library migrations run paged, undecryptable messages name the affected rows, task order survives restarts, and settlement obligations replay idempotently on startup.

## Security and scope

- Local-first remains unchanged: the new capabilities (task layer, preview, encryption) all run on the device with no central service;
- Cloud models still need explicit mail-content consent before they can search within that scope; external CLI/MCP keeps its read-only / send-confirmed / full-access tiers, and confirmations cannot be bypassed;
- The update trust root is unchanged: GitHub update assets continue to use Ed25519 manifest signature verification.

## Known issues and limitations

- **Outlook / Hotmail accounts cannot sign in on a default install (tracking Issue #120)**: Microsoft has disabled password authentication in favor of OAuth2 and the official build does not yet bundle an Azure OAuth client ID; set `NAMI_MAIL_MICROSOFT_OAUTH_CLIENT_ID` in `%APPDATA%\Nami Mail\nami-mail.env` as a temporary workaround.
- **Remote images and open tracking**: remote images load through the local proxy (the renderer never connects directly), but a sender can still observe opens through a unique image URL; "block by default / authorize per message / allow per sender" is a pending product decision.
- **Attachment preview boundaries**: legacy Office and HEIC/TIFF/PSD are not decoded (a download card explains why); PDF/scan rendering needs human visual acceptance; see item 13 of the known-limitations document.
- Windows x64 desktop only.
- Local search does not index attachment bodies; Chinese text is segmented per character.
- Cloud model and translation availability depends on the chosen third-party providers.
