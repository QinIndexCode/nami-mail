# Agent/RAG 迁移计划

[简体中文](migration-plan.md) | [English](migration-plan.en.md)

## 适用范围

本计划只处理 Agent 自有 `agent_*` 表、加密页面、来源事件、会话、确认、审计和 Provider 配置。它不重写既有邮件 schema、IMAP 缓存、SMTP outbox 或实验性本地 NLLB 翻译数据。

## 启动前条件

1. 只允许 `AgentHost` 在获得安全租约后打开生产数据库。
2. 在任何 Agent 读写前执行 `applyAgentStoreSchema`。
3. 迁移需要同一 SQLite 事务、足够磁盘空间和可关闭的同步/索引工作。
4. 迁移前生成可恢复的数据库备份或由安装器保留已验证备份；备份访问权限不得比原数据宽。

当前 schema 使用明确版本行，版本 `2` 支持从明确的版本 `1` 升级。未知表形状、缺失版本行、最小 reader 版本较新或运行时版本落后必须失败关闭，而不是猜测 ALTER 语句。

## 执行步骤

1. 将 Agent 入口置于排空状态，停止新 Broker/GUI 请求，等待现有写入结束。
2. 验证 SQLite 可打开、主密钥可用、当前 schema 版本和备份结果。
3. 运行版本化迁移；只有所有 DDL/DML 和形状检查成功后才更新版本行。
4. 运行只读完整性检查：账户生命周期、页面主键、来源事件状态/索引、会话/确认/审计触发器和 Provider 配置列。
5. 重新启动 Runtime，先以只读 health/read 工具 smoke，再恢复摄取和 GUI。

## V1 到 V2 的数据处理

V2 引入加密来源定位符与更严格的来源事件 claim 语义。旧版无法安全恢复定位符的未完成事件会被取消并标记可解释错误，而不是用模糊 ID 继续处理。账号 generation/删除事件可以安全恢复处理。页面表以明确迁移重建主键形状；迁移完成前 schema 版本不前进。

这意味着“继续处理所有旧 pending 工作”不是迁移目标。优先保证不会把错误邮件内容索引到错误账号；受影响 active 账号可由受控回填重建。

## 回滚与恢复

若迁移失败，事务回滚并保持旧版本；停止宿主并保留错误码/备份。若新版本已写入却发现应用缺陷，回滚应用二进制不等于可安全回滚数据库：只有针对该版本经过测试的反向迁移或备份恢复才能执行。不要手动删除 `agent_*` 表、修改版本行、复制旧 DEK，或在旧运行时上强制打开较新 schema。

## 数据保留

账号删除导致旧 DEK 不可用是设计的一部分。迁移、回滚和备份恢复不得复活已删除账号的 DEK 或 Agent 明文。物理删除密文仅在显式维护流程、保留窗口和审计要求均满足时进行。

## 验收

- 从空数据库、V1 fixture 和当前版本数据库分别验证启动。
- 每种失败注入后版本行与表形状保持一致。
- 迁移后原邮件同步/发送路径保持不变。
- 受影响 RAG 页面可以从仍存在的邮件源重建，已删除账号仍不可解密。
