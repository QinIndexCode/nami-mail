# 0003：收件人隐私与后台投递结果

[English](0003-2026-11-mail-result-correctness.en.md)

## 状态与范围

已采纳，2026-11-07。范围为收件人可见性、SMTP 结果、自动回复恢复、部分任务失败及相关契约。

## 背景

统一任务层已把发信从请求内操作改为后台执行，但部分调用方仍把受理等同于成功。审查还发现 mailto 将 BCC 转为 CC、部分 SMTP 拒收未保留。这些问题同时跨越输入契约、加密台账、任务执行与用户反馈，单改 toast 无法保证一致性。

## 决策

| 编号 | 决策 | 为什么 | 放弃了什么 |
|---|---|---|---|
| D1 | BCC 独立贯通撰写、草稿、确认和 SMTP，只存加密载荷 | 收件人可见性属于请求语义；草稿保留 Bcc 头，实际投递仅使用 envelope | 不把 BCC 降级成 CC，也不静默丢弃 |
| D2 | 逐收件人结果进入现有加密详情，重试草稿仅包含拒收地址并保留分组 | Sent 副本不证明所有地址均被受理 | 不通过整封重发修复部分拒收 |
| D3 | 自动回复持久关联 submission，按真实结果结算；未知投递保留待核对 | 限额、线程去重、审计与 UI 必须使用同一结果 | 不把排队作为成功，不自动重发未知投递 |
| D4 | 自动回复候选在同步事务中入持久队列，分批处理后继续；最终写入仍复用 tasks | 筛选/模型/等待用户不能占用账户远端写锁，输入也不能随通知丢失 | 不另建 SMTP 执行器，不把 40 封预算当作接受上限 |
| D5 | 任务关注项同时考虑终态与失败计数；日历与 MCP 使用有界分页 | 执行结束不等于全部成功；允许输入不能因首次查询上限静默消失 | 不用空面板或不完整工具目录表示正常完成 |
| D6 | 数据库读取门禁升为 v5；旧请求与旧加密载荷仍可读，无 BCC 请求保持原指纹 | 旧版 runner 无法解释 BCC，必须阻止它执行新请求 | 不支持 schema-v4 运行时打开升级后的数据 |

## 后果

现有任务层继续负责 SMTP/IMAP。自动回复增加持久业务输入与投递关联表，需运行时对账和关闭处理；出站详情增加兼容的可选字段。升级后的数据不能交给旧版调度器。

验证使用合成邮件、隔离 SQLite、真实本机 SMTP 和 stdio MCP，覆盖 BCC 头隐藏、部分拒收、旧请求幂等、45 封突发、待处理/未知投递重启、审批后中断、时区、分页、迁移以及前端反馈。

## 不属于本决策

完整备份恢复、OAuth 应用注册、发布信任、安装流程、外部日历同步和完整周期邀请支持。
