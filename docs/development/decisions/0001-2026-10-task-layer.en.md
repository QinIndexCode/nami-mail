# 0001 · One task layer and derived counts

[简体中文](0001-2026-10-task-layer.zh-CN.md) | [Decision index](README.en.md)

- **Status**: accepted (2026-10)
- **Scope**: server persistence and write paths, the HTTP contract, the web mail-list state
- **Replaces**: the `operation_queue` / `batch_jobs` / `batch_job_messages` tables and the five parallel approaches built around them

## Context

By 2026-09, "the user wants to change a message" had five independent server-side implementations: a single-message read flag, a batch move, a batch flag change, a scheduled send, and a draft discard. Each retried on its own, each tracked its own state, each decided on its own how to report failure to the web app. The consequences were predictable:

- When one batch failed halfway in two different places, the folders the UI showed and the rows in the database disagreed, and nothing could say how far that batch had actually got.
- Counts were written, not computed. `folders.total` / `folders.unseen` were maintained by eight ±1 bookkeeping sites, with six more local delta mirrors in the web app; a single missed update drifted permanently, and the drift only surfaced when a user counted the sidebar by hand.
- The send request blocked on SMTP until timeout, so the web app ran a forced full sync after it returned; the user saw "clicked send, spinner, whole page reloads".

These are not three bugs but three symptoms of one structural choice: **a user's intent had no first-class representation.**

## Decision

**Give user intent a table of its own, route every write path through it, and derive counts instead of storing them.**

| # | Decision | Why | Given up |
|---|---|---|---|
| D1 | `tasks` absorbs `operation_queue`, `batch_jobs`, and `batch_job_messages`; it does **not** absorb `outbound_submissions` | The first three describe the same thing — a batch of pending writes. The ledger does not: it records how far a message got in delivery, with a different lifecycle, and 42 named functions and 8 test files depend on it directly | "Tidy everything in one pass" would mean rewriting the ledger too, rebuilding the foreign key into `outbound_attachment_submissions`, and preserving the ticket path only deployed rows have |
| D2 | Drop the counting semantics of `folders.total` / `folders.unseen`; every count is derived from `messages` (`folder-counts.ts`) | A stored count needs every write site to be correct; a derived one needs a single query to be correct | Every sidebar refresh now runs a real query (measured within budget, see Consequences); no more illusion of a free cached read |
| D3 | `POST /api/messages/send` answers 202 immediately, SMTP moves into a background task, and draft discard becomes a child task of the send | The request no longer blocks on the network, and the web app no longer needs a forced full sync after it | The web app must handle the "accepted but not yet sent" state |
| D3b | The send writes one local optimistic Sent row in the **same transaction**, flagged `pending_send`; when sync pulls the provider's Sent copy it claims that row through an **HMAC lookup column** instead of inserting a duplicate | 202 only fixes "the request is blocked", not "it is not visible after sending": there was no local row at all until a sync ran | The claim key must be an indexable plaintext lookup column — `messages.message_id` is always NULL once encrypted and cannot serve. Hence `remote_id_lookup`: the same input as the ledger's `rfc_message_id` under a different derivation, and the two are not comparable |
| D4 | The provider seam is a **thin adapter**: `context.providers` is the injection point, while `mail.ts` keeps its module-level mockability | 34 test files and roughly 377 cases depend on mocking `mail.js`, `imapflow`, or `nodemailer` | Pure constructor injection is "cleaner", but it would rewrite all 29 files that mock `mail.js`; the risk outweighs the gain |
| D5 | Keep `messages.pending_move_*` (it is the target state itself, and generated columns and partial indexes depend on it); keep `pending_flags_push` / `pending_flags_base_json` as the unconfirmed local target, but move **retry state into `tasks`** | Target state belongs to the message, retry belongs to the task; mixing them in one table is exactly what produced the five parallel approaches | Message rows still carry "what I want to become", and the read model has to know that |
| D6 | Introduce no derived-count cache table | Plain queries measured fast enough (worst unified-inbox shape 39.80ms, full sidebar refresh 1.30ms per account, both inside the p95 ≤200ms budget) | No cache invalidation to get wrong, and no cold-cache cliff |
| D7 | **Two counting domains**: badge counts are derived (same domain as the list); `folders.remote_total` / `remote_unseen` stay, written only by sync's STATUS overwrite, and used only for "synced M of N" hints | `SYNC_MESSAGE_LIMIT` defaults to 2000, so local `messages` is a **truncated mirror**: a derived `total` is systematically smaller than the provider's truth | Two sets of numbers coexist, and comments and docs must say which one may be used as "the total" |

## Consequences

**Gained:**

- A batch operation has a single state machine: accepted means persisted, each account advances serially, failures carry an `error_code`, and the UI polls tasks instead of guessing.
- Sidebar counts and the list are always in the same domain — same table, same derivation — so drift no longer depends on someone remembering to write one more place.
- Send returns immediately, the Sent list shows a row at once, and the provider copy merges into it rather than duplicating it.
- Tests can assert "run → settle" for one task kind instead of asserting the individual failure branches of five separate paths.

**Paid:**

- `TASK_KINDS` lists eight kinds and only five have runners. `draft-discard`, `filter`, and `agent-apply` are reserved: drafts and filter rules still execute synchronously, and agent writes reuse the injection seams of send/flags/move. A stored kind with no runner is settled as `failed` / `no_runner` the first time the scheduler sees it, so it never sits pending forever.
- The three `/api/batch-jobs` endpoints survive as compatibility aliases until the renderer and the end-to-end tests have all moved to `/api/tasks`.
- The migration is not a plain `INSERT … SELECT`: the legacy `payload_json` / `patch_json` are plaintext, sealing them needs the master key, and the migration point must therefore run after the key is ready.
- `SCHEMA_VERSION` moves from 2 to 3: an older process refuses to open a database a newer one has migrated. That is the only rollback guardrail for "unify once", and it means downgrading means reinstalling the old version and accepting an unreadable database.

**How it is verified:** the target invariants (which no batch may violate) and the per-batch test guardrails live in the module comments under `apps/server/src/tasks/` and in `apps/server/tests/task-*.test.ts`; the counting measurements are in `apps/server/tests/folder-counts.test.ts` and the performance baseline.

## Out of scope

- **Whole-database at-rest encryption**: a separate storage/privacy batch running at the same time, orthogonal to this decision (it changes how the file is encrypted, not how writes are routed).
- **The agent tool surface**: it reuses these injection seams, but tool scope and consent boundaries are their own decision.
- **Web framework and styling**: `mailStore` is where "one store" landed, but this decision only requires that counts and the list share a source, not how React is organised.
