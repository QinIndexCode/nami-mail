# 0001 · 统一任务层与派生计数

[English](0001-2026-10-task-layer.en.md) | [决策记录索引](README.zh-CN.md)

- **状态**：已采纳（2026-10）
- **范围**：服务端持久化与写路径、HTTP 契约、前端邮件列表状态
- **替代**：`operation_queue` / `batch_jobs` / `batch_job_messages` 三张表与围绕它们的五套写入风格

## 背景

到 2026-09 为止，"用户要改一封邮件"这件事在服务端有五条彼此独立的写法：单封已读标记、批量移动、批量标志、定时发送、草稿丢弃。它们各自重试、各自记状态、各自决定失败怎么告诉前端。后果是可预测的：

- 同一批操作在两处半途失败时，界面显示的文件夹与数据库里的行不一致，而且没有单一处能判断"这批到底做到哪一步"。
- 计数是写的，不是算的。`folders.total` / `folders.unseen` 由 8 个 ±1 写入点维护，前端另有 6 处本地 delta 镜像；任何一处漏写就永久偏差，而偏差只有在用户数一遍侧边栏时才会被发现。
- 发信请求被 SMTP 阻塞到超时，前端在响应回来后强制全量同步一次；用户看到的是"点了发送，转圈，然后整页重载"。

这些不是三个 bug，而是同一个结构选择的三种症状：**一批用户意图没有一等公民的表示**。

## 决策

**引入一张任务表承载"用户意图"，把所有写路径收敛到它之上；计数改为派生，不再有计数列。**

| # | 决策 | 为什么 | 放弃了什么 |
|---|---|---|---|
| D1 | `tasks` 吸收 `operation_queue`、`batch_jobs`、`batch_job_messages`；**不吸收** `outbound_submissions` | 前三者表示的是同一种东西（一批待执行的写入）。台账不是：它记录的是"这封信投递到哪一步"，与任务的生命周期不同，且已有 42 个具名函数与 8 个测试文件直接依赖 | 想"一次美化到底"就得连台账一起重写，并重建 `outbound_attachment_submissions` 的外键关系与已部署行的票根路径 |
| D2 | 删除 `folders.total` / `folders.unseen` 的计数语义，计数一律由 `messages` 派生（`folder-counts.ts`） | 写出来的计数需要每个写入点都正确，派生值只需要一个查询正确 | 每次侧边栏刷新都有一次真实查询（实测在预算内，见后果）；不能再有"零成本读缓存"的错觉 |
| D3 | `POST /api/messages/send` 立即 202，SMTP 移入后台任务，草稿丢弃变成发送的子任务 | 请求不再被网络阻塞，前端不必在响应后强制全量同步 | 前端要处理"已受理但未发送"这个中间态 |
| D3b | 发送时在**同一事务内**写一条本地乐观 Sent 行，带 `pending_send` 标记；sync 抓回服务商 Sent 副本时按 **HMAC 查找列**认领它，而不是插入重复行 | 202 只解决"请求被阻塞"，不解决"发完看不到"：本地原本不存在行，要等一次 sync 才出现 | 认领键必须是可索引的明文查找列——`messages.message_id` 在加密后恒为 NULL，不能用；因此引入 `remote_id_lookup`（与台账的 `rfc_message_id` 同输入、不同派生键，两者不可比较） |
| D4 | provider 接缝以**薄适配**为主：`context.providers` 是注入点，同时保留 `mail.ts` 的模块级可 mock 性 | 34 个测试文件、约 377 个用例依赖对 `mail.js` 或 `imapflow` / `nodemailer` 的 mock | 纯构造函数注入更"干净"，但会让那 29 个 mock `mail.js` 的文件全部重写，收益不抵风险 |
| D5 | `messages.pending_move_*` 保留（它就是目标态，生成列与部分索引都依赖它）；`pending_flags_push` / `pending_flags_base_json` 保留为"未确认本地目标"，但**重试状态移到 `tasks`** | 目标态属于消息，重试属于任务；把两者混在一张表里正是原来五套写法的根因 | 消息行仍然携带"我要变成什么"，读模型需要知道这一点 |
| D6 | 不引入派生计数缓存表 | 纯查询实测足够快（统一收件箱最坏形态 39.80ms，侧边栏全量刷新 1.30ms/账户，均在 p95 ≤200ms 预算内） | 没有缓存失效问题可写，也就没有"缓存没热时突然变慢"的余地 |
| D7 | **计数口径分两套**：徽标计数=派生值（与列表同域）；`folders.remote_total` / `remote_unseen` 保留，唯一写入者是 sync 的 STATUS 覆盖写，只用于"已同步 M / 共 N" | 默认 `SYNC_MESSAGE_LIMIT=2000`，本地 `messages` 是**截断镜像**：派生 `total` 会系统性小于服务商真值 | 两套数字并存，必须靠注释与文档说清哪一个能用作"总数" |

## 后果

**得到：**

- 一批操作有了单一状态机：受理即落表，每个账户串行推进，失败有 `error_code`，界面轮询任务而不是猜测。
- 侧边栏计数与列表永远同域——两者读同一张表、同一个派生规则，偏差不再可能靠"某人记得多写一处"来避免。
- 发信立即返回，Sent 列表里马上有行，服务商副本到达后归并而非重复。
- 测试可以针对一个任务种类断言"执行→结算"，而不必逐个断言五条写路径各自的失败分支。

**付出：**

- `TASK_KINDS` 词表有 8 种，当前只有 5 种有 runner。`draft-discard`、`filter`、`agent-apply` 是预留：草稿与过滤规则仍同步执行，Agent 写入复用 send/flags/move 的注入接缝。已存但没有 runner 的 kind 由调度器首次见到即结算为 `failed` / `no_runner`，不会永远停在 pending。
- `/api/batch-jobs` 三个端点作为兼容别名保留，直到渲染层与端到端测试全部迁到 `/api/tasks`。
- 迁移不是纯 `INSERT … SELECT`：旧 `payload_json` / `patch_json` 是明文，加密封装需要主密钥，而迁移点必须落在密钥就绪之后。
- `SCHEMA_VERSION` 从 2 升到 3：旧版进程会拒绝打开被新版迁移过的库，这是"一次性统一"唯一的回退护栏，也意味着降级必须重装旧版并接受数据库不可读。

**验证方式：** 目标不变量（任何批次都不得违反）与逐条测试护栏记录在 `apps/server/src/tasks/` 的模块注释与 `apps/server/tests/task-*.test.ts` 中；计数口径的实测数字见 `apps/server/tests/folder-counts.test.ts` 与性能基准。

## 不属于本决策

- **整库静态加密**：这是同期另一条独立的存储/隐私批次，与本决策正交（它改的是文件加密方式，不改写路径）。
- **Agent 工具面**：复用本决策的注入接缝，但工具作用域与同意边界是另一个决策。
- **前端框架与样式**：`mailStore` 是"单一 store"的落地，但本决策只要求"计数与列表同源"，不规定 React 组织方式。
