# 设计规范（Design System）

本文档定义界面必须遵守的**视觉基线**。在此之前，视觉规则只隐含在
`apps/web/src/styles.css`（约 17,000 行）里，导致同一层级出现多套阴影、同一语义出现多档字号——
每轮局部收敛，全局继续发散。新增或修改样式前先读本文档。

- 样式事实来源：`apps/web/src/styles.css`
- 主题：`:root`（浅色）与 `:root[data-theme=dark]`（深色），语义 token 两套成对定义
- 修改视觉的验证方式：`npm run test:e2e`（3 套 spec）、`npm run smoke:desktop`，以及读取样式文件的断言测试

## 1. 阅读字宽（measure）

| token | 值 | 用于 |
|---|---|---|
| `--measure` | `672px` | 阅读区所有居中列 |

阅读区（`.mail-title`、`.mail-content`、`.translation-panel`、`.verification-code-list`、
`.attachment-list`）是**同一个居中列**，必须共用 `--measure`；任一块单独设宽都会让文字边缘错位。

**推导方式**：672px 减去 48px 左右内边距 = 约 576px 正文；正文字体是 Georgia 16px，
混合散文平均字宽约 8px → 约 **72 字符/行**，落在长文阅读的舒适区（45–75 字符）。

> 若正文字体或字号改变（`.mail-text, .mail-html` 的 `font-family` / `font-size`），**必须重算 `--measure`**。
> 这也是为什么不在这里使用 `ch`：`ch` 以声明该属性的元素自身的字体为准，而容器（`.mail-content`）
> 继承的是 UI 字体，用它算出的宽度会严重偏小。

## 2. 圆角

| token | 值 | 用于 |
|---|---|---|
| `--radius-sm` | `8px` | 大多数控件：按钮、输入框、列表行、标签、卡片内块 |
| `--radius-md` | `12px` | 面板级：浮层、菜单、对话框、较大的卡片 |
| `--radius-lg` | `20px` | 大面板/外层容器档（当前无引用，保留为第三档） |
| `--radius-pill` | `999px` | 胶囊：状态徽标、开关、头像、圆点 |

**不要写字面数值**。允许的例外只有"刻意的不对称圆角"（例如
`border-radius:var(--radius-md) var(--radius-md) 4px` 表示只圆上方两角）——即便如此，
其中的每一档也必须引用 token。

## 3. 阴影

| token | 用于 |
|---|---|
| `--shadow-sm` | 贴合在内容上的小控件：拖动拇指、内嵌卡片 |
| `--shadow-raised` | 浮起于内容之上的层：菜单、气泡、下拉、工具条 |
| `--shadow` | 最高层：模态、大浮层 |
| `--shadow-drawer` | 从侧边滑出的抽屉 |

判断顺序是**"它离内容面多远"**，而不是"看起来要多重"。同一层级的两个浮层必须用同一个 token。

**什么**不在**这个体系里**（不要硬套 token）：

| 类别 | 写法 | 说明 |
|---|---|---|
| 细线/内高光 | `inset 0 1px 0 …` | 是描边与质感，不是高度 |
| 焦点环 | `0 0 0 3px var(--focus-ring…)` | 见 §7 |
| 分隔线 | `0 1px 0 var(--line)` | 可与其他层并列出现 |
| 状态光晕 | `0 Npx Mpx color-mix(in srgb, var(--token) X%, transparent)` | 选中/悬停/错误/辉光的**着色**抬升，必须由 token 混出，不能用裸色值 |
| 原生控件细节 | 如 `::-webkit-slider-thumb` | 平台渲染细节 |
| `none` | — | — |

**现状（已收敛，2026-09-10）**：全库 105 处 `box-shadow` 字面量里，**80 处属于上表的细线/焦点环**，
25 处是候选高度阴影。其中 **12 处已折进 token**（菜单/浮层 6 → `--shadow-raised`，卡片级 6 → `--shadow-sm`），
并因此**删掉了 2 条多余的深色主题覆盖规则**——token 自身按主题切换，字面量才需要覆盖。
现在**高度阴影字面量为 0**；剩余字面量全部是 18 处状态光晕 + 2 处原生滑杆细节。

> 修正此前的说法：早先记的"约 100 处一次性阴影"把 80 处细线/焦点环算了进去，实际待收敛量是 25 处候选、
> 真正常要处理的 12 处。教训是**按类别统计，而不是按关键字计数**。

## 4. 字号

**基线原则：同一语义必须同档，不主张整体放大。**
本项目是信息密集的桌面邮件客户端，8–11px 的小字号（计数、时间戳、元信息）是产品定位，
不是缺陷；需要治理的是"同一类信息用了不同档位"。

当前取值分布（`styles.css`）：`8px`(28) / `9px`(81) / `10px`(155+) / `11px`(144+) /
`11.5px`(2) / `12px`(52) / `12.5px`(3) / `13px`(11) / `13.5px`(1) / `14px`(9) / `15px`(10) /
`16px`(7) / `18px`(3) / `20px`(4) / ≥26px 若干。

**待收敛**：
- 消除五个孤立半像素值：`9.5px`(3) / `10.5px`(1) / `11.5px`(2) / `12.5px`(3) / `13.5px`(1)（贴回相邻整数档）。
- `9px` 与 `10px` 混用需要判定：同类元信息统一到一档（建议 `10px`）。
- 正文字号固定 16px（阅读区衬线正文）。

## 5. 行高

| 场景 | 值 |
|---|---|
| 阅读区正文（`.mail-text, .mail-html`） | `1.7` |
| 标题（`.mail-title h2`） | `1.24` |
| UI 文本 | `1.3`–`1.45` |
| 清零用（图标行等） | `0` / `1` |

正文此前是 `1.85`，对 16px 字号偏松，长段落显得散。**无单位数值是默认写法**；
确需 `px`/`em` 时（如配图标行高）在注释里说明原因。

## 6. 配色

### 语义色：降饱和的"灰调"
`--danger` `--success` `--warning` `--info` 是刻意降饱和的墨色档
（浅色 `#b43838` / `#347a4a` / `#b67816` / `#4f7294`），深色主题**不是简单反相**，
而是提亮并重新调饱和（`#e47070` / `#75b98a` / `#d49233` / `#7ba1c4`）。这是基线，继续保持。

### 强调色：必须与语义色同饱和度区间
`--cal-*`（日历六色）当前是**未降饱和的原色**（`#3b82f6` / `#a855f7` …，近似 Tailwind 500）。
与语义色同屏时会出现"高级灰 + 刺眼原色"的断层。

**待收敛**：给 `--cal-*`（以及附件图标色）做一次降饱和，纳入与语义色相同的饱和区间；
深色档同步调整。新增强调色默认按此办理。

### 对比度下限（有测试强制）
本项目的字号普遍在 8–11px，**没有任何文字够得上 WCAG 的"大字"豁免**，所以全部按普通文本的
**4.5:1** 下限要求。`apps/web/src/themeContrast.test.ts` 会从 `styles.css` 里读取 token 并逐个校验：
文字三档（`--text` / `--text-soft` / `--text-faint`）在 `--panel-solid`、`--panel`、`--panel-muted`
以及 `--canvas`（`.background-preview` 会把 faint 文字直接画在 canvas 上）上都必须达标；
语义四色（`--danger` / `--success` / `--warning` / `--info`）在三种面板上达标（它们不会落在裸 canvas 上）。

建立基线时据此修掉了两个浅色 token：
- `--text-faint`：`#727279` → `#66666c`（在 `--panel-muted` 上 4.38 → 5.01，在 canvas 上 4.49 → 4.82）
- `--warning`：`#b67816` → `#9a6510`（在面板上 3.69 → 4.95）

> 已知边界：面板是半透明的，且可以叠加自定义壁纸——把面板不透明度调低又配深色壁纸时，
> 上述比值会被打破。默认 `--bg-panel-opacity:100%`，测试按"面板合成在 canvas 之上"计算。

### 层级与描边
- 弱分隔（列表行、卡片内的线）用 `--line`；
- 强界定（外层容器、模态、需要被看见的边框）用 `--line-strong`；
- 不要在同一元素上把两系叠着用（例如 `--line-strong` 再 `color-mix` 一次 `--line`）。

## 7. 交互状态

控件应覆盖的态：`hover` / `active` / `disabled` / `selected`（或 `.active`）/ `focus-visible`。

- **焦点环**：全局兜底规则已覆盖 `button/input/textarea/select:focus-visible`，
  所以自定义控件**不必**再写一份重复的环；需要自定义外观时用
  `:focus:not(:focus-visible)` 去掉指针焦点的轮廓 + `:focus-visible` 单独给环（参考 `.mail-title h2`）。
- **`:disabled`**：只要控件在代码里可能出现 `disabled`，就必须有对应样式。
  新增可禁用控件时一并补上，不要留给后续补丁段落。
- 禁止裸 `outline:none`：必须与 `:focus-visible` 的替代环成对出现。

### `!important` 的使用纪律

这个文件里的 `!important` **多数是必需的**，属于以下四类结构性场景，不要以"清理"为名删除：

| 场景 | 原因 |
|---|---|
| 覆盖邮件自带的内联样式（如 `.mail-html table` 的 `max-width`） | 内联样式优先级高于普通外部规则，只有 `!important` 能压过 |
| 全局 `user-select` 管控（`.workspace-canvas *` 关、输入区/正文/预览区开） | 与另一条 `!important` 对抗，必须同级 |
| `@media (prefers-reduced-motion)` 与 `print` | 必须压过所有组件的动画/过渡 |
| `.theme-transitioning` 关闭过渡 | 切换主题时临时压过全部过渡 |

**除此之外不要再用 `!important`**：如果是为了压过"特异性更高的变体规则"（例如 `.foo>div` 这类组合选择器），
正确做法是**写更具体的选择器**，而不是加 `!important`。示例（2026-09-10 按此模式改掉一处）：

```css
/* 之前：用 !important 硬压 */
.sidebar-footer-actions { gap:2px!important }
/* 之后：靠特异性取胜，并注明在压谁 */
/* Beats `.sidebar-footer>div{gap:8px}` (0,1,1) on specificity. */
.sidebar-footer>.sidebar-footer-actions { gap:2px }
```

> 修正：审计曾估"约 6 处 `!important` 冗余"，逐条核查后**不成立**——被点名的那些要么是上表的结构性场景，
> 要么正在与更高特异性的规则竞争（如 `.sidebar-footer>div`）。真正可静态证明冗余的只有 1 处，已按上述模式消除。
> 其余 53 处的移除需要**浏览器级级联验证**（计算样式逐条对照），风险与收益不匹配，保留并以棘轮锁定不再增长。

### 间距目标修正：不是 4px 栅格，而是 2px 子栅格

审计原先把"间距归一到 **4px** 栅格"列为待收敛项。实际测量后**这个目标不成立**：
`gap`/`padding`/`margin` 里的 887 个"离 4px 栅格"值中，绝大多数是 **2px 的倍数**
（`6px`153、`10px`168、`14px`62、`18px`35、`22px`18…），另有 `1px`/`3px` 用于描边与光学微调。

也就是说这套布局是**手工按 2px 子栅格调过的**，强行改成 4px 会让间距整体变化 —— 那是**对设计做改造，
不是还债**。因此实际执行的规则是：

- `7px`/`9px` 这类"离所属档位只差 1px 的手抖值"全部归到 `8px`（已完成，其余数不允许再出现）；
- 其余**奇数值节奏**（`5px`/`11px`/`13px`/`17px`/`15px`/`19px`/`21px`/`25px`/`29px`/`41px`，共 205 处）
  以棘轮预算锁定，只允许下降，**不允许新增**；
- `1px`/`3px` 视为描边/微调，永久豁免。

## 9. 变更流程

1. 改样式前对照本文档，确认改动落在已有档位上；需要新增档位时**同时更新本文档**。
2. 视觉类改动跑 `npm run test:e2e`（含侧栏、列表、更新页脚三套）+ `npm run smoke:desktop`。
3. 涉及"多像素级"收敛（上表待收敛项）时，先补视觉基线再动手。

## 10. 自动化基线（`apps/web` 的两个测试）

规则要有东西盯着才成立，所以基线是**可执行的**，随 `npm test` 一起跑：

| 文件 | 作用 |
|---|---|
| `src/themeContrast.test.ts` | 从 `styles.css` 读 token，按主题计算 WCAG 对比度并卡 4.5:1 下限（见 §6） |
| `src/designTokens.test.ts` | 圆角/阴影/字号/`!important`/`outline` 策略 + **债务棘轮** + 主题齐备性 + 文档存在性 |
| `e2e/geometry.spec.ts` | **几何基线**：4 个断点 × 侧栏/列表行高/阅读列宽/正文宽度，外加"任何断点都不得横向溢出"；另有一条主题不改变 measure、且深色正文确实是浅色的断言 |

### 几何基线（`e2e/geometry.spec.ts`）

| 断点 | 侧栏 | 阅读列 | 正文宽 | 列表行高 |
|---|---|---|---|---|
| 1440px | 238px | 1116px | `--measure` 672 → 正文 576 | 105px |
| 1000px | 220px | 694px | 672 → 612 | 105px |
| 800px | 抽屉（280px，移到画面外） | 744px | 672 → 612 | 105px |
| 600px | 抽屉（画面外） | 600px（全屏） | 556 | 105px |

断言是**紧的（±2px）**：如果某个改动让这些数字变化，那是**有意的**，应当连同理由一起改这里的常量——
这正是这份文件存在的意义。存量收敛（阴影/字号/间距）改完像素后，用它对照即可判断是改好还是改坏。

> 顺带记一条交互顺序约定（由这轮基线发现并修复）：**首次运行的条款门必须先于更新提示出现**。
> 此前 toast 层与更新提示会盖在条款对话框上，窄窗下"同意并继续"点不动。
> 现在条款门算作打开的模态（`dialogRouting` 的 `anyModalOpen`），提示层据此退后。

**棘轮（ratchet）的含义**：`designTokens.test.ts` 顶部的 `debtBudget` 记录的是**存量债务的上限**——
圆角越界值、状态光晕、半像素字号、`!important`、裸 `outline` 各自的数量。它只允许**下降**：

- 修掉若干处 → **同步把预算数字调小**（这是收敛的进度记录）。
- 任何时候都不许调大；新增一处越界值会直接失败（例如再写一个 `border-radius:7px`，
  因为 7px 不在预算表里，测试立刻报错）。
- 四种圆角档位之外，只允许 `0 / 2px / 4px / 50%` 这类结构性取值。
- 阴影是**按层（layer）**判定的契约而不是计数：每个浮层要么是四种高度 token、要么是 §3 表格里
  的豁免类别。所以"新增一处裸色值阴影"会直接失败，而状态光晕只需遵守 recipe（另有数量棘轮）。

这份棘轮**不替代**视觉基线：它拦的是"新增越界"，不是"存量收敛"。存量收敛会改变像素，
仍需按 §8 前置条件走。
