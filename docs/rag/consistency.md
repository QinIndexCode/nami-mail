# RAG 一致性

[简体中文](consistency.md) | [English](consistency.en.md)

## 必须保持的事实

1. 每个活动页面属于一个当前存在且 active 的账号 generation。
2. 每个页面修订可追溯到一个消息来源修订和清洗/分块版本；当前没有附件正文页面或附件页面修订。
3. 已删除页面不进入检索；旧 generation 也不进入检索。
4. 同一事务内的邮件状态变更与来源事件要么一起提交，要么一起回滚。
5. 来源事件 claim 只能由一个工作者完成；重试、取消和完成具有可恢复状态。
6. 内存检索结构可被清空和重建，不是事实来源。
7. 账号 DEK 丢弃后，不存在恢复旧 Agent 明文的“修复”路径。

## 验证层级

**轻量运行时检查**：读取/写入时验证 schema 版本、账号 generation、页状态、内容摘要和 AAD；不匹配即拒绝。

**维护检查**：在显式 `rag verify`/维护任务中统计 pending/failed/cancelled 事件、找出缺页或旧版本活动页、检查页面来源修订、确认内存结构只含可读活动页。验证默认只读，不应自动重建或删除。

**修复流程**：先停止相关账号的新摄取，记录诊断摘要，选择受限回填/重建，验证新页面和引用，再淘汰旧页。无法解密的已删除账号数据只报告为已撤销，不尝试修复。

## 崩溃恢复

崩溃在事务提交前：邮件与事件都不存在；提交后：事件可从 `pending` 或恢复的失败状态继续。工作者不能把“开始处理”视为“已完成”。如果进程重启丢失内存索引，只从当前可解密页面重建；不得从日志或 Provider 缓存恢复邮件正文。

## 观察指标

记录无敏感内容的指标：事件状态数量、最久 pending 时间、重试次数、每账号页面数、检索延迟、内存结构大小、版本分布和拒绝原因。超过预算时降速或暂停回填，不删除用户数据来掩盖问题。

参见 [故障排查](troubleshooting.md) 和 [测试计划](../development/testing-plan.md)。
