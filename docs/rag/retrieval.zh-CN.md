# RAG 检索

[简体中文](retrieval.zh-CN.md) | [English](retrieval.en.md)

## 查询边界

检索请求必须先有已验证的 caller、账户范围和当前账号 generation。先应用权限和 scope，再查询页面；不能先在全库召回、再在 UI 中过滤。已删除、旧 generation、内容摘要不匹配或无法解密的页面不会成为候选。

## 当前检索

当前运行时使用词法词项评分和结构化范围过滤，并在词法无结果时以**查询扩展**作为第二路检索。它会先验证账号范围、当前 generation、消息限制和页面状态，再从持久化 SQLite 倒排表（`agent_rag_index`）按查询词取 postings 并用 BM25 打分生成词法候选，仅对 top 候选池解密 payload；当词法臂没有任何候选（或最高分低于阈值，该阈值默认关闭）时，向用户配置的默认对话 Provider 请求该问题的同义/领域/跨语言检索词，再用这些词查询同一个倒排表，两路候选通过倒数排名融合（RRF）合并后复核引用。持久页保持加密；词法索引为 Agent store 的 SQLite 倒排表（只存 token 与 tf 计数），**查询扩展不产生任何索引侧存储——没有向量、没有嵌入、没有冷启动重建**。

推荐流程：

1. 规范化查询并限制长度、账户、时间/文件夹等过滤器和结果数量。
2. 读取当前 generation 的活动页面，计算词法候选；仅在词法无结果（或低于阈值）时才请求扩展词并计算第二路候选。
3. 融合并排序候选，按来源/修订复核，施加结果与页面上限。
4. 验证页面仍可解密且来源仍属于当前范围。
5. 输出带稳定分数解释和引用的结果；Provider 只得到被选择的最小上下文。

## 来源引用

每项结果应包含账号、消息或页面标识、来源修订、块索引、必要片段和应用内跳转信息。引用不是模型回答的“可信证明”：UI 应允许用户打开原邮件、选择/复制文本，并明确指示索引可能过时或清洗过。

## 查询扩展与隐私边界

第二路检索是**查询扩展**，不是向量检索：中文等无词边界的语言里，用户问法与邮件写法经常一个字符都不重合（「报销」与「费用申请」），任何纯词法调优都跨不过去，因此词法臂无结果时（或最高分低于阈值时，该阈值默认关闭）会用当前默认**对话** Provider 生成该问题的一批检索词——同义词、领域词、中英对照——再用这些词查询同一个本地倒排表。**只有用户的问题文本会发给 Provider，邮件正文与片段始终留在本机**：扩展不读取、也不外发任何页面内容。

隐私边界：

- 扩展请求只包含用户的问题文本，发往用户配置的默认 Provider；Provider 为 Ollama 等本机服务时端点被限制为回环地址，问题文本也不离开本机。
- 云端端点（如 HTTPS 的 OpenAI 兼容服务）与对话共用同一授权边界：云端 Provider 未开启"允许云端处理邮件内容"（`allowCloudMailContent`）时，整段检索不会运行，扩展请求也不会发出。
- 扩展是尽力而为且有硬超时（800ms）：Provider 不可用、超时、返回格式非法、用户取消，都等同于"没有额外检索词"，检索退回纯词法，既不会中断也不会让回复明显变慢。同一问句的扩展词有界缓存，重复提问不重复调用。
- 扩展不产生索引：没有向量、没有第二条明文副本、没有冷启动重建成本。检索面完全由既有的加密页面与本地倒排表承担。

## 性能和降级

查询需要有时间、内存和候选数量预算（扩展调用含 800ms 硬超时）。倒排索引缺失或损坏、Provider 不可用、页面暂未就绪或账户正在删除时，应返回可解释状态而非部分越权结果。不得通过持久化明文缓存来改善冷启动；词法索引落盘不改变这一边界——索引表只存派生 token，正文仍只存在于加密页与内存。

第二路的实际收益是可观测的：`GET /api/agent/rag/verify` 返回的一致性报告带 `expansion` 计数——`triggered`（词法无结果而触发扩展的次数）、`recovered`（扩展救回结果的次数）、`empty`（扩展也未能救回）。在决定是否降低扩展阈值或扩召回预算之前，应先读这三个数。
