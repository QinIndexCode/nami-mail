# RAG 检索

[简体中文](retrieval.zh-CN.md) | [English](retrieval.en.md)

## 查询边界

检索请求必须先有已验证的 caller、账户范围和当前账号 generation。先应用权限和 scope，再查询页面；不能先在全库召回、再在 UI 中过滤。已删除、旧 generation、内容摘要不匹配或无法解密的页面不会成为候选。

## 当前检索

当前运行时使用词法词项评分和结构化范围过滤，并在默认模型 Provider 可提供嵌入时启用混合检索。它会先验证账号范围、当前 generation、消息限制和页面状态，再从持久化 SQLite 倒排表（`agent_rag_index`）按查询词取 postings 并用 BM25 打分生成词法候选，仅对 top 候选池解密 payload；若启用了语义检索，则页面与查询都经用户配置的默认 Provider 嵌入端点计算向量，词法与语义候选通过倒数排名融合（RRF）合并后复核引用。持久页保持加密；词法索引为 Agent store 的 SQLite 倒排表（只存 token 与 tf 计数），语义索引为进程内内存结构，两者均可从页面和来源事件重建。

推荐流程：

1. 规范化查询并限制长度、账户、时间/文件夹等过滤器和结果数量。
2. 读取当前 generation 的活动页面，计算词法候选；若已启用语义检索，同时以同一查询向量计算语义候选。
3. 融合并排序候选，按来源/修订复核，施加结果与页面上限。
4. 验证页面仍可解密且来源仍属于当前范围。
5. 输出带稳定分数解释和引用的结果；Provider 只得到被选择的最小上下文。

## 来源引用

每项结果应包含账号、消息或页面标识、来源修订、块索引、必要片段和应用内跳转信息。引用不是模型回答的“可信证明”：UI 应允许用户打开原邮件、选择/复制文本，并明确指示索引可能过时或清洗过。

## 语义检索与 Embedding 边界

语义检索是已接线的可选能力：默认模型 Provider 为 `openai-compatible` 或 `ollama` 类型时，若配置了 `embeddingModel`（缺省回退到对话模型）且云端端点已获显式授权，RAG 工作者会把每个检索页面的主题、发件人与正文发给该 Provider 的嵌入端点，向量存入进程内语义索引；查询时以同一端点嵌入查询文本，并与词法候选做 RRF 融合。

隐私边界：

- 嵌入的邮件文本只发往用户配置的默认 Provider 端点；Provider 为 Ollama 等本机服务时，端点被限制为回环地址，邮件文本永不离开本机。
- 云端端点（如 HTTPS 的 OpenAI 兼容服务）外发邮件文本与对话、词法检索共用同一授权边界，需要用户在模型配置中显式开启"允许云端处理邮件内容"（`allowCloudMailContent`）。
- 向量仅存于进程内：不落盘、不作为第二个明文副本；页面删除、代际变更或 Provider 切换时同步清除，冷启动后从活动页面重建。
- 嵌入是尽力而为：页面嵌入失败仅使该页缺失于语义索引（词法仍覆盖）；查询嵌入或融合失败时整体回退纯词法检索，检索不会因语义链路不可用而中断。

## 性能和降级

查询需要有时间、内存和候选数量预算。倒排索引缺失或损坏、Provider 不可用、页面暂未就绪或账户正在删除时，应返回可解释状态而非部分越权结果。不得通过持久化明文缓存来改善冷启动；词法索引落盘不改变这一边界——索引表只存派生 token，正文仍只存在于加密页与内存。
